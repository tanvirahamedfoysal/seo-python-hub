\section{Executive summary}

\begin{keybox}
The cleanest mental model is \textbf{one product with two experiences}: Jinja2 is the public, search-friendly website; Flutter is the authenticated application. FastAPI remains the single HTTP entry point, and both experiences use the same business services and repositories.
\end{keybox}

This plan turns that model into an implementable repository, URL contract, request flow, deployment process, and staged roadmap. It intentionally keeps the boundaries strict:

\begin{itemize}
  \item Public, indexable content lives at ordinary URLs such as \texttt{/topics/python-functions}.
  \item Small authenticated enhancements use HTMX endpoints under \texttt{/web-components/...}.
  \item Rich authenticated workflows live below \texttt{/app/...} and are rendered by Flutter Web.
  \item JSON endpoints live below \texttt{/api/v1/...}; WebSocket endpoints, if needed later, live below \texttt{/ws/...}.
  \item Neither frontend talks directly to the database. Both call shared application services.
\end{itemize}

\section{Product goals and architectural principles}

\safeheading{What the product should feel like}
The visitor should be able to discover and read Python learning content without an account and without requiring JavaScript. A signed-in learner should be able to continue into a more interactive application for progress, bookmarks, statistics, discussions, notifications, and other stateful features.

\safeheading{Non-negotiable principles}
\begin{enumerate}
  \item \textbf{One domain and one backend entry point.} Use a domain such as \texttt{pythonlearninghub.com}; let FastAPI decide which renderer handles each path.
  \item \textbf{Presentation is separate from business logic.} Jinja2 and Flutter may render the same concept differently, but they must not implement separate copies of the rules.
  \item \textbf{Public pages remain useful without JavaScript.} HTMX improves them; it must not be their only way to work.
  \item \textbf{URLs reveal ownership.} The path prefix is a routing contract, not an informal convention.
  \item \textbf{Build the smallest useful version first.} Redis, WebSockets, chat, and advanced moderation are later capabilities, not prerequisites for the public learning site.
\end{enumerate}

\safeheading{Recommended technology choices}

\section{The two-experience model}

\safeheading{Public website: Jinja2 plus HTMX}
Use server-rendered pages for content that people may discover through search or share directly:

\begin{itemize}
  \item home page, roadmap, categories, tags, tutorials, guides, and topic pages;
  \item public discussion pages and useful search results;
  \item explanatory content, examples, exercises, and related-topic navigation;
  \item simple actions such as bookmark, mark complete, reply, or filter, enhanced with HTMX when appropriate.
\end{itemize}

\safeheading{Application: Flutter Web}
Use Flutter under \texttt{/app} for workflows whose value comes from client-side state and rich interaction:

\begin{itemize}
  \item login, dashboard, profile, progress, bookmarks, and activity history;
  \item learner statistics, charts, filters, and multi-step workflows;
  \item richer discussions, notifications, chat, and administration when those features justify it.
\end{itemize}

\begin{notebox}
Do not force every feature to exist in both frontends. A topic can have an SEO-friendly public page and an API representation for Flutter without requiring two separate user interfaces for every action.
\end{notebox}

\safeheading{What FastAPI manages}
FastAPI is the composition point. It mounts routers, configures dependencies, serves templates and static files, exposes JSON endpoints, and returns the Flutter entry document for routes below \texttt{/app}. The route handlers should remain thin: authenticate, validate, call a service, and choose a response representation.

\safeheading{A request to a public topic}
\begin{enumerate}
  \item The browser requests \texttt{GET /topics/python-functions}.
  \item FastAPI dispatches to the public topic router.
  \item The router calls \texttt{TopicService.get\_by\_slug(...)}.
  \item The service calls \texttt{TopicRepository}; the repository reads PostgreSQL.
  \item The router passes the result to Jinja2 and returns complete HTML.
\end{enumerate}

\safeheading{A request from Flutter}
\begin{enumerate}
  \item Flutter requests \texttt{GET /api/v1/progress} with the authenticated session.
  \item FastAPI resolves the current user and validates the request.
  \item The API router calls \texttt{ProgressService}.
  \item The service uses the same repository layer and returns a response schema.
  \item FastAPI serializes JSON; Flutter updates its state.
\end{enumerate}

\safeheading{A transition from Flutter to public content}
When a learner selects an SEO-oriented topic, Flutter can navigate the browser to \path{/topics/python-asyncio}. FastAPI then returns the public Jinja2 page. The learner has moved between two presentations without moving between domains or duplicating the content source.

\section{FastAPI composition and routing}

\safeheading{Application composition}
The central module should make the routing boundary obvious. The following is intentionally schematic; exact framework versions and database libraries can be selected during implementation.

\begin{lstlisting}[language=Python,caption={Composition point in \texttt{main.py}}]
from fastapi import FastAPI

from app.routers.api.v1 import router as api_router
from app.routers.web.pages import router as web_router
from app.routers.web.components import router as component_router
from app.flutter import mount_flutter_web

app = FastAPI(title="Python Learning Hub")

app.include_router(web_router)
app.include_router(component_router, prefix="/web-components")
app.include_router(api_router, prefix="/api/v1")
mount_flutter_web(app, prefix="/app")
\end{lstlisting}

\safeheading{Flutter fallback behavior}
Flutter uses client-side navigation. A request to \texttt{/app/dashboard} therefore needs the same Flutter entry document as \texttt{/app/}. The mounting helper should:

\begin{enumerate}
  \item serve real generated assets such as JavaScript, icons, and canvaskit files;
  \item return Flutter's \texttt{index.html} for an application route that is not a physical asset;
  \item never catch \texttt{/api}, public pages, or HTMX endpoints;
  \item use an explicit prefix so a missing asset cannot silently become a public HTML page.
\end{enumerate}

\begin{lstlisting}[language=Python,caption={Conceptual Flutter route fallback}]
@router.get("/{path:path}")
async def flutter_route(path: str):
    requested = flutter_root / path
    if requested.is_file():
        return FileResponse(requested)
    return FileResponse(flutter_root / "index.html")
\end{lstlisting}

\begin{notebox}
The fallback is deliberately scoped below \texttt{/app}. A global catch-all route is a common source of broken public pages, incorrect 404 behavior, and difficult debugging.
\end{notebox}

\section{Shared services and data flow}

\safeheading{One concept, two representations}
For a topic with slug \texttt{python-functions}, expose two representations:

\safeheading{Service responsibilities}
Services should answer product questions rather than framework questions. Examples include:

\begin{itemize}
  \item \texttt{TopicService}: locate, publish, search, and relate learning content;
  \item \texttt{AuthService}: register, authenticate, rotate sessions, and resolve account state;
  \item \texttt{ProgressService}: mark a lesson complete, calculate progress, and record activity;
  \item \texttt{BookmarkService}: add, remove, and list saved items;
  \item \texttt{DiscussionService}: create, edit, moderate, and retrieve discussion content.
\end{itemize}

\safeheading{Thin route handler example}
\begin{lstlisting}[language=Python,caption={A public route that delegates to a service}]
@router.get("/topics/{slug}", response_class=HTMLResponse)
async def topic_page(request: Request, slug: str, service: TopicService = Depends()):
    topic = await service.get_published_by_slug(slug)
    if topic is None:
        raise HTTPException(status_code=404)
    return templates.TemplateResponse(
        request=request,
        name="topics/detail.html",
        context={"topic": topic},
    )
\end{lstlisting}

\safeheading{Rendering rules}
\begin{itemize}
  \item Keep page-level templates responsible for layout and metadata.
  \item Keep component templates small enough to return as an HTMX response.
  \item Use semantic headings in order; do not use font size as a substitute for document structure.
  \item Provide visible focus states, keyboard access, labels for form controls, and useful empty/error states.
  \item Treat user-authored discussion content as untrusted; escape by default and sanitize only through a deliberate policy.
\end{itemize}

\section{Authentication and authorization}

\safeheading{Recommended first approach}
Use a secure, same-site session cookie for the browser-facing product. FastAPI dependencies can resolve the current user for both HTML routes and API routes. If a separate mobile client is required later, add a token-based API flow without changing the service boundary.

\begin{enumerate}
  \item Hash passwords with a modern password-hashing library; never store plaintext passwords.
  \item Set cookies as Secure in production, HttpOnly, and an intentional SameSite policy.
  \item Add CSRF protection to cookie-authenticated state-changing browser requests, including HTMX requests.
  \item Check authorization in services or dedicated policy functions, not only in templates.
  \item Make admin and moderation roles explicit and auditable.
\end{enumerate}

\begin{lstlisting}[language=Python,caption={Conceptual dependency usage}]
@router.post("/progress/{topic_id}")

        request=request,
        name="components/progress_button.html",

\end{lstlisting}

\safeheading{API client discipline}
Flutter should use a small typed API client. Keep endpoint paths, serialization, error mapping, and authentication behavior in one place. Widgets should not assemble raw URLs or interpret database-shaped responses directly.

\section{Search engine optimization}

\safeheading{Public-page checklist}
Every indexable page should have:

\begin{itemize}
  \item a unique, descriptive title and meta description;
  \item one clear H1 and a logical heading hierarchy;
  \item canonical URL handling;
  \item meaningful internal links between related topics;
  \item server-rendered content in the initial response;
  \item useful 404 and no-result pages;
  \item structured data only when it accurately describes the page;
  \item a sitemap and robots policy that reflect publication state.
\end{itemize}

\begin{successbox}
The SEO rule is simple: if a page is valuable to someone who has not signed in, make it a real Jinja2 URL. Flutter can link to it, but search engines should not need to boot Flutter to read it.
\end{successbox}

\section{Development and deployment workflow}

\safeheading{Local development}
Run the backend and Flutter source project independently during development. The public website and API can run on FastAPI while Flutter uses its normal development server. Configure the API base URL so the Flutter client can call the local backend.

\begin{lstlisting}[caption={Conceptual local workflow}]
Terminal A: backend development server on localhost:8000
Terminal B: Flutter development server
Database: local PostgreSQL instance or development container
\end{lstlisting}

\safeheading{Build script responsibilities}
Create \texttt{scripts/build\_flutter.py} or an equivalent task runner that:

\begin{enumerate}
  \item runs the approved Flutter Web build command;
  \item validates that \texttt{build/web/index.html} exists;
  \item replaces the generated backend Flutter directory in a controlled way;
  \item copies the build artifact into \texttt{backend/app/flutter/web};
  \item reports the build hash and output path;
  \item fails before deployment if required files are missing.
\end{enumerate}

\begin{notebox}
Generated output should be reproducible and disposable. Do not hand-edit generated JavaScript or put secrets in Flutter assets; Web assets are publicly downloadable.
\end{notebox}

\safeheading{Release checks}
Before production deployment, confirm:

\begin{itemize}
  \item all migrations apply cleanly to a fresh database;
  \item public pages return useful HTML with JavaScript disabled;
  \item direct refreshes of \texttt{/app/dashboard} and other Flutter routes work;
  \item unknown \texttt{/app} assets return an appropriate response;
  \item API errors are consistent and do not leak database details;
  \item cookies, CSRF protection, CORS, and trusted-host settings match the deployment;
  \item the generated Flutter artifact is present in the deployment package;
  \item no secrets, local paths, or debug settings are included in the release.
\end{itemize}

\section{Security and operational safeguards}

\begin{itemize}
  \item Validate all input at the API boundary and enforce domain rules in services.
  \item Parameterize database queries; never interpolate user input into SQL.
  \item Apply rate limits to authentication, search, comments, and expensive endpoints.
  \item Limit upload size and file type if user uploads are introduced.
  \item Log request identifiers, authentication failures, moderation actions, and unexpected errors without logging secrets.
  \item Back up PostgreSQL and test restoration before relying on it.
  \item Add health checks that verify application availability and database connectivity.
  \item Keep dependency updates regular and review security advisories.
\end{itemize}

\section{Phased implementation roadmap}

\safeheading{Phase 1: public learning site}
Build the smallest useful product first:

\begin{itemize}
  \item FastAPI, PostgreSQL, migrations, configuration, and deployment skeleton;
  \item Jinja2 base layout, home page, roadmap, topics, categories, and search;
  \item service and repository boundaries for content;
  \item metadata, sitemap, 404 page, accessibility, and responsive styling;
  \item tests for public routes and content queries.
\end{itemize}

\safeheading{Phase 2: accounts and lightweight learner actions}
\begin{itemize}
  \item registration, login, logout, password recovery, and session handling;
  \item progress and bookmarks through services and repositories;
  \item HTMX buttons for simple actions on public pages;
  \item API schemas and versioned routes for the same data.
\end{itemize}

\safeheading{Phase 3: Flutter application}
\begin{itemize}
  \item create the Flutter source project and typed API client;
  \item implement login, dashboard, profile, progress, and bookmarks;
  \item add the reproducible build-and-copy workflow;
  \item mount the compiled output under \texttt{/app} and test direct route refreshes.
\end{itemize}

\safeheading{Phase 4: discussions and administration}
Add public discussions, replies, reports, moderation state, admin screens, audit events, and role-based access. Decide feature by feature whether simple actions remain HTMX or move into Flutter.

\safeheading{Phase 5: real-time and scale features}
Only after the core product is stable should you add Redis, WebSockets, chat, notifications, background jobs, search indexing, caching, or more advanced analytics.

\section{Common mistakes to avoid}

\begin{enumerate}
  \item Putting Dart source files inside the Python application directory.
  \item Creating different business rules for Jinja2 and Flutter.
  \item Making public topic content depend on Flutter booting successfully.
  \item Adding a global catch-all route that steals 404s from the public website.
  \item Returning database models directly as API contracts.
  \item Putting raw SQL in route handlers or Flutter widgets.
  \item Introducing WebSockets and Redis before the basic learning workflow is validated.
  \item Treating generated Flutter output as hand-maintained source.
  \item Forgetting that every browser-delivered Flutter asset is public.
\end{enumerate}

\section{Definition of done}

The first production-ready milestone is complete when:

\begin{itemize}
  \item a visitor can browse and search useful Python content with JavaScript disabled;
  \item the same domain serves public pages, HTMX fragments, JSON, and Flutter below clear prefixes;
  \item a signed-in learner can record progress and bookmarks;
  \item Jinja2 and Flutter consume the same service and repository rules;
  \item direct navigation and refresh work for public and Flutter URLs;
  \item automated tests cover the primary content and authentication flows;
  \item deployment can rebuild the Flutter artifact instead of relying on manual file edits;
  \item logging, backups, migrations, security settings, and error handling are documented.
\end{itemize}

\begin{keybox}
The core rule to keep visible while implementing is: \textbf{one domain, one FastAPI backend, two deliberate presentation layers, shared services, and a staged roadmap}. That gives the project the SEO benefits of server-rendered content without giving up the richer interactions that Flutter is good at.
\end{keybox}
